### 3.1 关键判读修正：为什么「中间卡」可能其实是「开头卡」

- **插值感知修正**：四个动画共用 `decelerate_cubic`（`in_fwd.xml:9` 等）。减速曲线前段速度最高：t=17%（≈30ms）时进度已达 43%，t=33%（≈60ms）进度 70%。
- 因此：**动画起点（头 1–3 帧）发生的主线程停顿，视觉上表现为「页面已冲出去大半 → 停一下 → 慢慢收尾」** —— 正是用户口述的「前半段流畅、中间卡一下、后半段流畅」。
- 影响：§1.1-E2「开头帧问题应卡在开头」的排除判读**不严谨**，开头成本经减速曲线折射后会呈现为中段卡顿。但这不等于 E2 复活为重建（重建已消除）；它使 **H2（进入方向的事务执行成本）** 重新入列，并让探针数据的时间对齐成为唯一裁决手段（探针时间戳不撒谎，观感会折射）。

### 4.0 探针日志格式变更（2026-10-06 第二轮：归因增强）

> 背景：第一轮 `SLOW_MSG` 行只记 `callback` token（数字型消息恒为字面 `null`），把
> 「提交这条消息的 Handler」信息整个丢了 —— 真机新出现的 45ms `what=159` 无法归因。

- **旧格式**（第一轮）：`SLOW_MSG <target> what=<what> <ms>`。其中 `<target>` 取的是
  `msg.callback`（Runnable 派发时有类名；**数字型消息恒为字面 `null`**，且因系统 printer
  串为 `callback + ": "` 而**带尾随冒号**，如 `null:`）。
- **新格式**（本次）：`SLOW_MSG h=<handler简单类名> c=<callback简单类名> what=<what> <ms>`。
  新增 `h=` 记「提交该消息的 Handler 简单类名」（取自 dispatch 行 `Handler (<全类名>)`
  括号内，如 `h=ActivityThread$H`）；`c=` 为去掉尾随冒号后的 callback 简单类名
  （数字型消息仍为字面 `null`，保持可 grep）。取不到时回退 `unknown` / `null` / `-1`（handler / callback / what 三字段分别对应）。
- **新增 `MARK` 行**：`MARK <tag>`。`NavHost` 在 `open()` 转场前与 `back()` 弹栈前各写一行
  （tag 形如 `nav.open:<目标页简单类名>` / `nav.back`），用于把 `LONG_FRAME` / `SLOW_MSG`
  对齐到「哪一次导航」；探针关闭时 `PerfProbe.mark()` 只读一次开关即返回，零开销、不落盘。
- **本轮真机指纹（新包 c294cd5，11:37 窗口，二级页转场过程中）**：H2 指纹
  （`FragmentManager$5` 事务消息 16–25ms ×4）**消失**（P0-2 方向有效）；H1 指纹
  （`Choreographer$FrameDisplayEventReceiver` 22→26ms）**仍在**；**新增一条 45ms 的
  `what=159` 待归因** —— 因旧格式丢失 Handler 类名而无法定位，正是本次格式增强的直接动因。
  领先候选为框架 `ActivityThread$H.EXECUTE_TRANSACTION = 159`，但**待新格式日志证实，
  不在代码内写死断言**。
  ⚠️ **更正（第三轮，2026-10-06）**：其中「H2 消失」的结论已被第三轮真机数据推翻
  （7/7 次 `nav.open` 稳定复现 16–24ms）——第二轮仅采到 4 条即判「消失」，属**采样假象**。
  详见下「第三轮：v3 格式」。

### 4.0.（续）第三轮：v3 格式（2026-10-06）

> 动因：第二轮新包（`h=` 格式）的全量真机日志暴露两处盲区 ——
> ① `SLOW_MSG h=unknown c=null what=-1` 能落盘却归因不了（`>>>>> Dispatching to` 行到了、
> 但 `DISPATCH_RE` 未命中，原始串被丢弃）；② 时间戳在**落盘线程**生成，跨行只能对齐到
> 「哪次导航」，分辨不出同一笔消息内部的子阶段。

三处变更（仅 `perf/PerfProbe.kt`，纯观测、零业务耦合、默认关闭）：

1. **`@<uptimeMs>` 统一时钟**：每行尾追加 `@<uptimeMs>`，值为 `write()` 在**主线程调用点**
   采样的 `SystemClock.uptimeMillis()`（**绝不**在落盘线程取）。三种来源（`LONG_FRAME` /
   `SLOW_MSG` / `MARK`）均带，可精确相减、复原子阶段先后。

—— 这直接否定了「事务开销来自排队」的旧猜法。

**（2）消息内部分解：视图创建占 ~70%**

| 子阶段 | 口径（`PerfProbe.kt:276-278`） | 耗时 | 占消息比 |
|---|---|---|---|
| `created → viewCreated` | onCreate + onCreateView（inflate） | **12–14ms** | **~70%** |
| `viewCreated → resumed` | onViewCreated + onStart + onResume | 5–6ms | ~30% |

> 【待核实】`frag.viewCreated` 与 `Fragment.onViewCreated` 的先后（决定 `onViewCreated` 落哪个桶）：
> androidx 源码 `FragmentStateManager.createView()` 内 `performViewCreated()` 与
> `dispatchOnFragmentViewCreated()` 的调用次序**未在本机核实**（无 JDK / 无 gradle 缓存 / 联网取源码失败）。
> **但无论归属哪桶，结论不变**：`created→resumed` 共 18–20ms，且**视图构造占绝对多数**、
> `onStart/onResume` 只占 5–6ms。

**（3）结构性根因首次拿到直接证据：`back` 销毁顶层页 → 每次进入都重付 inflate**

| # | `nav.back` | `frag.paused` | `frag.stopped` | `frag.viewDestroyed` | `frag.destroyed` | `stopped→viewDestroyed` |
|---|---|---|---|---|---|---|
| 1 | 4485210 | +0 | +2 | +193 | +193 | 193ms |
| 2 | 4491450 | +1 | +43 | +189 | +189 | 146ms |
| 3 | 4497478 | +0 | +2 | +198 | +199 | 196ms |

- **back 路径确实销毁顶层页**（`viewDestroyed` + `destroyed`）→ 下次 `open` 必然全新 inflate。
  这是上一轮「每次进入全额重建」推论的**实测确认**。
- `stopped→viewDestroyed` = 146–196ms ≈ **`out_back` 的 180ms**（`out_back.xml:9`）→ 销毁被退出动画
  推迟，属**设计行为**、非缺陷（也印证 P1 硬件层对此无效）。
- **back 路径零 `SLOW_MSG`** → 弹栈执行（remove 顶层 + show 下层）本身便宜；且 back 之后
  **没有 `frag.created` 重放** → **keep-alive「返回零重建」不变量成立**，从推测升级为**已证**。

**（4）`nav.open→frag.created` 的 15–20ms 无任何慢消息覆盖**

该空档**没有任何 `SLOW_MSG`** → 不是某个长任务，而是**这条消息被推迟到下一帧才执行**
（点击帧被输入派发占用，`commit()` 投递的是同步消息，受主线程 synchronization barrier 约束）。
【待核实：机制推断，需一次定向实验证实】
- 性质：它是**交互延迟**（点完到动画开始之间的静默），**不是掉帧**；
- 约束：`commitNow()` **不能与 `addToBackStack()` 并用**（框架抛异常），故在现有
  「异步 commit + 回退栈」结构下这段延迟**不能靠换 API 移除**。

**（5）第三轮的 dwell 期 `Choreographer` 簇（66.7ms）本轮未复现**

3 个 dwell 段（4.1s / 4.5s / 1.0s）内**零日志行**（无 `LONG_FRAME`、无 `SLOW_MSG`）。
→ 该现象或为**偶发**、或为上一轮**采样假象**。**本轮不列它为修复目标**（是否追查见 §七 Q3）。

**（6）量级结论**

单次进入 = `nav.open → frag.resumed` ≈ **33–39ms ≈ 2.0–2.3 帧**（60Hz）：

| 桶 | 耗时 | 性质 | 可削减性 |
|---|---|---|---|
| 事务消息被推迟到下一帧 | 15–20ms | 交互延迟（不掉帧） | 低（受 `commit+addToBackStack` 结构约束） |
| **视图创建（inflate）** | **12–14ms** | **掉帧主因** | **高** |
| `onStart + onResume` | 5–6ms | —— | 低 |

> **掉帧的机械成因**：事务消息 18–20ms **> 16.7ms 帧预算** → 该帧超支 → 进入动画起手必掉 1 帧
> （= 用户说的「进入瞬间一顿」）。**唯一的可动大头是 inflate 的 12–14ms**：压到 ~8ms 以下，
> 消息即回到 16.7ms 内，起手掉帧消失。
>
> 页面体量（`fragment_settings.xml` 实码核实）：**419 行 / 6 分组 / 14 个 `<include>`
> （12× `row_setting_value` + 2× `row_setting_switch`）/ 0 个 ViewStub**；`row_setting_value`
> = 4 view/行（`row_setting_value.xml:13-42`），include 子树贡献 **~48 view**；2 个
> `SwitchMaterial`（构造成本高于普通控件）。
>

> （`status_detail` / `plan_review` / `debug`）是否同量级**未采样** → 建议下一轮顺带做体重对照（§五 P2-3）。

## 4.1 第五轮（用户真机复测反馈）：转场位移被「微推」化 —— 根因与修订（2026-10-06 下午）

**用户新观察（原话）**：
> 进入二级页面时，页面从右滑入，等到了左侧快收尾的时候会卡顿两下；退出二级页面的时候，从左侧划入右侧，似乎只滑动了三分之一的距离然后页面直接消失。

### A. 退出「只滑 1/3 就消失」—— 确定性几何缺陷（已修）

**现象** = 页面平移了一小段后整体**凭空消失**。

**根因**（可证）：
- 四个动画 XML 的位移**都只有 22%**（§三 A5）：`in_fwd` 22%→0、`out_fwd` 0→-22%、`in_back` -22%→0、`out_back` 0→22%。
- `FragmentTransaction` 的 `hide(frag)` 语义 = **退出动画播完后把该页视图置 `View.GONE`**。
- `out_back` 只走 22% ⇒ 动画结束时退出的二级页 **仍有 78% 宽度盖着屏幕**，此刻被置 GONE ⇒ 屏幕右侧 78% 的整块内容**同帧消失** → 用户描述「只滑三分之一就直接消失」。
- 几何补充：`back()` 是 `hide(顶层)+show(下层)` 同时播（`setReorderingAllowed(true)`）；上层只走 22% 时，其左侧 22% 条带此刻露出的是下层页，故消失区域在视觉上更像「页面被截断」。

**为什么 22% 是「语义漂移」而非设计意图**：设计原型 `docs/prototypes/prototype.html:434-435`
```css
@keyframes in_fwd{from{transform:translateX(22%);opacity:.3}to{transform:none;opacity:1}}
@keyframes in_back{from{transform:translateX(-22%);opacity:.3}to{transform:none;opacity:1}}
```
原型是「**22% 位移 + 透明度 0.3→1 淡入**」的复合效果 —— 位移很小，靠淡入托住。Android 侧为消除双窗口「叠影」**禁用了 alpha**，只剩光秃秃的 22% 位移 → 既不是原型效果，也不再是「转场」，沦为「微推」。这正是 §1 纪律「原型 = 设计意图 ≠ 实现现状」的又一例。

**修订**（2 个文件）：`in_fwd` `22%`→`100%`、`out_back` `0→22%`→`0→100%`。两层 22% 视差（`out_fwd`/`in_back`）**保留** —— 与原型「方向性」意图一致，且即 iOS 标准手感（上层整屏进出、下层轻微视差）。

**几何自洽性（修订后无露底、无突跳）**：设进度 p∈[0,1]（`%` 按容器宽）——
- 进入：上层（新页）左缘 = (1-p)·100%，下层（旧页）右缘 = 100-22p。需 `下层右缘 ≥ 上层左缘`：`100-22p ≥ 100-100p` ⇔ `p ≥ 0` 恒真 ⇒ **恒被盖住，不露底**。
- 退出：上层（离场页）左缘 = 100p，下层（返回页）右缘 = 78+22p。需 `78+22p ≥ 100p` ⇔ `p ≤ 1` 恒真 ⇒ **恒被盖住，不露底**；p=1 时上层已移出屏右，置 GONE 不可见 ⇒ **无突跳**。
- 首开（容器为空，无下层）：仅 `in_fwd` 生效，新页自屏右整屏滑入，期间露出的下层 = `pageContainer` 之后的 tab 页 —— 与「二级页盖住 Tab」的既有语义一致。

### B. 进入「收尾卡两下」—— 【待真机验证】主因待定，但已收窄

**与 A 的区分**：A 是动画几何（确定性、已修）；B 是动画窗口内的**掉帧**，需新数据判读。收窄范围：
- 事务消息内联 inflate（18–24ms，v3 已证在**起手**掉 1 帧，见 §4.0 续2）—— 位置不符「收尾」，**基本排除为主因**。
- **异步内容回填落在动画窗口内**：以 `SettingsFragment` 为例，`observe()` 起 **6 个** `repeatOnLifecycle(STARTED)` 流（`SettingsFragment.kt:224-320`），其中 `renderGoals` / `renderReminders` 会 `removeAllViews()` 后**重新 inflate 整组行**（`:384-481`、`:796-828`）—— 这些都在 `onViewCreated` 之后异步落到主线程，若落在 180ms 窗口内即掉帧；**两次重渲染 ≈ 用户描述的「两下」**。
- 方案 B 只治**复用**路径的 inflate；**首开**仍全额 inflate（见 §五 P1-B），故若用户测的是首开，方案 B 本就不覆盖首开开销。

**下一步**：真机 v3 探针复测（协议同 §4.0 续2：进 → 停 3 秒 → 回 ×3 + 快速进出 ×3），按「违例落在哪两条 `MARK` 之间」定位 B 的主因；若确认是内容回填，按 P0-1 先例（`postDelayed` 出动画窗口）逐页处理。

### C. ① 流式输出（新增能力，两条路径都覆盖）

改造口径：**不新增分支** —— 非流式 = `sink == null`，与流式共用同一份 prompt 组装 / 重试 /
降级链路。据此三条既有契约全部不动摇：

| 契约 | 为什么不破 |
|---|---|
| prompt **字节冻结**（金样本 `pipeline/prompt_golden.py`） | 只改传输方式，**一个字节的 prompt 都没改** → 不递增 `PROMPT_VER_CHAT` / `PROMPT_VER_CHAT_TOOL` |
| 埋点「一次往返恰一行 `llm_calls`」 | 流式仍是一次 HTTP 往返（`QuotaGuard` 按行数计）→ 零改动 |
| 「绝不抛异常」 | 异常分类 / 重试 / 降级结构原样复用 |

链路（5 文件）：

| 文件 | 改动 |
|---|---|
| `net/LlmProvider.kt` | 新增 `StreamSink` 接口（`:156`，`onDelta(text)` + 默认空实现的 `onReset()`）与 `chatStream(request, sink)`（`:206`）；新增 `STREAM_CALL_TIMEOUT_MS = 120s`（`:210`）—— 长流不能被一次性请求的 `callTimeout` 腰斩 |
| `net/OpenAiCompatProvider.kt` | `singleCall` 参数加 `sink`，`Accept` 头切 `text/event-stream`；`isEventStream()` 判定后走 `readEventStream()`（`:288`，手读 SSE，不加依赖）；工具调用按 `tool_calls[].index` **分片累积** `function.arguments` |
| `ui/ChatEngine.kt` | 新增 `replyStream(..., sink)`（`:138`），`reply(...)` 整体委托它（`sink = null`） |
| `agent/HealthAgent.kt` | `run(...)` 末尾加 `sink`（`:1547`），**每轮 provider 往返前 `sink.onReset()`**（`:1585`） |
| `ui/ChatViewModel.kt` / `ui/AssistantFragment.kt` | `_streaming: StateFlow<String?>` 暴露全量正文；列表末尾挂一条**临时助理气泡**渲染它，落库后交接 |

**两条关键不变量（都是「不靠模型自觉」的机械保证）**：

1. **只有最终答复可见**：工具循环的中间轮（查数据）模型随手的文字**不推给 UI** —— 每轮
   `onReset()` 清空累积，只有**终止轮**（Done / ProposalPending）之后不再重置（`:1540`）。
2. **流式气泡与落库消息无闪烁交接**：两条异步流（Room Flow 发射 vs `_streaming` 置 `null`）
   到达顺序不定，故气泡**不靠调用方掐时机撤下**，而是「`streamDone` 为真 **且** 下一次
   `submit` 到达」时才撤（`AssistantFragment.kt:550`）；显示与否另由
   `persistedCatchesUp()`（末尾助理消息是否已以这段正文开头）兜住。

**⚠️ 中途断流不得重试**（本轮自审发现并修复的真缺陷）：流式下 `readTimeout` 是**块间空闲
超时**，长流卡住会抛 `SocketTimeoutException` —— 此时正文可能已吐了半段。若按「可重试」
处理，重试会往**同一个** sink 追加增量 → 用户看到**正文重影**。修法：新增 `EmitFlag`
（`OpenAiCompatProvider.kt:149`）把「已吐过增量」从异常里带出来，`singleCall` 的**每个**
catch 分支都回填 `emitted.value` → `chatInternal` 据此放弃重试（`:120`）。
