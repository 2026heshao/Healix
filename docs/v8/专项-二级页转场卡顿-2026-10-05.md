### 3.1 关键判读修正：为什么「中间卡」可能其实是「开头卡」

- **插值感知修正**：四个动画共用 `decelerate_cubic`（`in_fwd.xml:9` 等）。减速曲线前段速度最高：t=17%（≈30ms）时进度已达 43%，t=33%（≈60ms）进度 70%。
- 因此：**动画起点（头 1–3 帧）发生的主线程停顿，视觉上表现为「页面已冲出去大半 → 停一下 → 慢慢收尾」** —— 正是用户口述的「前半段流畅、中间卡一下、后半段流畅」。
- 影响：§1.1-E2「开头帧问题应卡在开头」的排除判读**不严谨**，开头成本经减速曲线折射后会呈现为中段卡顿。但这不等于 E2 复活为重建（重建已消除）；它使 **H2（进入方向的事务执行成本）** 重新入列，并让探针数据的时间对齐成为唯一裁决手段（探针时间戳不撒谎，观感会折射）。

| **H2（事务执行成本 + 感知偏移）** | **坐实，主因** | 每次导航一笔 `FragmentManager$5` 消息 16-25ms（4 次/6 秒，与采集节奏一致）；事务执行与动画起点同刻（A4）+ decelerate 折射（§3.1-A）→ 「中段卡」观感 |
| **H3（status_detail 联动刷新）** | 部分坐实（被 H2 吸收） | `FragmentManager$5` 功能性身份 = 事务执行 Runnable（`execPendingActions` 路径；匿名类序号对应 androidx.fragment ≈1.8.x 源码）。⚠️ 版本纠偏（2026-10-06）：`androidx.fragment` **未在 `app/build.gradle` 直接声明**（仅间接经 `appcompat 1.7.0` / `material 1.12.0` / `lifecycle 2.8.7` 传递解析），故原文推断的「≈1.8.x」**存疑**；实际传递版本待 CI `./gradlew :app:dependencies` 确认（代理报 **1.5.4**）。已确证：本工程**无** `fragment-ktx` / `activity-ktx`。status_detail 的 collector 重绑若命中也计入这笔消息，P0-1 继续有效 |
| **H1（整层光栅化）** | **坐实，次因** | `Choreographer$FrameDisplayEventReceiver 22ms` = doFrame 本身慢（重绘开销），随后 LONG_FRAME——与 H1 预期指纹「LONG_FRAME + Choreographer 类 target」吻合；但 6 秒内仅 1 次，量级低于 H2 |
| H4 / H5 | 排除 | 全片段无任何其他 target 的 SLOW_MSG（无 widget/Service/Inflater 类名） |
| H6（系统级） | 暂排除 | 每条 LONG_FRAME 都有明确 SLOW_MSG 对应，无「孤立无解释长帧」 |

#### 4.3.3 量级算术与 P0 数据支撑

- 帧预算 16.6ms：事务执行 25ms → **必然掉 2 帧**（33.3ms 长帧），落在 180ms 动画（10.8 帧）中段即占 1/6 时长——与症状逐字吻合。
- `FragmentManager$5` 耗时 25/16/16/18ms，**贴着 16ms 阈值波动**：P0-2（`setReorderingAllowed(true)`，削减事务同步生命周期粒度）+ P0-1（status_detail refresh 延后出窗口）把这笔开销砍回 16ms 以下的预期收益明确。
- H1 侧的 doFrame 22ms 是低频次因 → P1 硬件层方案保留，待 P0 落地复测后看剩余 LONG_FRAME 再决定是否追加。

**结论：第一轮指纹完整命中 §三 矩阵的 H2（主）+ H1（次）组合，H4/H5/H6 排除。P0 三项获得数据支撑（Q1 拍板状态更新见 §七）。**
