### 问题 1 · 二级页面退出仍有卡顿 —— 修复未彻底

**现状**：需求 1 的主根因（二级页 = 独立 Activity 双窗口转场）已消除：现在二级页是 `pageContainer` 上的 Fragment，转场只剩 180ms 纯 `translate`（`anim/in_back.xml`、`out_back.xml`，`duration=180`）。前进路径已无明显卡顿，**退出仍卡**。

**根因候选**（按嫌疑排序，本机无设备无法复现，需真机定位）：

1. **异步弹栈的空窗帧**：`NavHost.back()` 用异步 `popBackStack()`（`NavHost.kt:95-99`，为让 `out_back` 播完）——按下返回后要先等下一帧事务才执行、动画才开播；当帧主线程若忙，感知就是「点了没反应一拍」。
2. **二级页 → 二级页 的返回要重建下层页**：`NavHost.open` 用 `replace + addToBackStack`（`NavHost.kt:86-87`），弹栈回下层二级页时其 `onCreateView` 重新 inflate（无视图复用），布局 14–23KB 的页面会掉帧。
3. **退出瞬间下层页观察者集中回刷**：如 `MineFragment` 的读库渲染在退出动画期间切回主线程。
4. 输入法收起与退出动画同帧抢主线程。

**下一步（动作序列）**：真机抓 `adb shell dumpsys gfxinfo com.healix.app` / Perfetto 复现退出 1 秒的主线程 → 确认候选 → 修复候选 1 可改 `popBackStackImmediate()` 并手动补退出动画；修复候选 2 可把「二级页 → 二级页」改 `show/hide` 复用。

**完成判据**：真机二级页退出无可感知停顿（无 >2 帧掉帧）。

### 问题 2 · 热量目标无设置项 + 目标仍有默认预置 —— 两个独立缺口

**2a：热量目标不在「目标」栏（从未覆盖，入口错位）**

- 设置页「目标」栏的槽位唯一来源 `GoalSlots.ALL`（`db/GoalEntities.kt:120-130`）只有：主目标 / 体重 / 每周训练 / 睡眠 / 饮水 **5 槽位，没有热量**。
- 截图里「今日盈余 · 目标 2500」读的是 settings 键 `TARGET_KCAL`（`MainViewModel.kt:186-189`），兜底 `GoalDefaults.TARGET_KCAL = 2500`（`GoalEntities.kt:173`）。
- 它**有**编辑入口，但在**个人信息页**（`PersonalInfoFragment.kt:71` `rowTargetKcal`）——用户去目标栏找，自然找不到。功能存在、位置错误。

**修复方向**：新增 `GoalSlots.KCAL`（metric `kcal_daily`；`goals` 表加行只是数据，**零 schema 改动、零迁移**）→ 目标栏可增删改；`HealthAggregator.kt:164-165` 与 `MainViewModel` 的读取源从 settings 键切到 `goalDao`；老用户已设的 `TARGET_KCAL` 做一次性搬迁（读到旧键 → 写入目标行），不丢用户数据。

**2b：目标仍有默认预置（修复未彻底）**

- `ensureReminderDefaultsIfEmpty()`（提醒默认）T04 已删 ✅；
- ~~但 `ensureGoalDefaultsIfEmpty()` 仍在 `SettingsViewModel` 的 `init` 里跑~~ —— **此自述已过时，现况以代码为准（✅ 已随问题 2 修复，commit `68162d1`）**：该函数已**整体删除**（删除说明 `SettingsViewModel.kt:198-201`）；`SettingsViewModel` 的 `init` 现只跑 `migrateLegacyKcalTarget()` + `reload()`（`SettingsViewModel.kt:155-167`，定义于 `:180`）——全新安装不再静默预置 6 行默认目标，主目标只由首启引导 `GoalSetupSheet` 落一行。

**修复方向（✅ 已拍板）**：删掉 6 行种子；主目标保留「首次进入引导设置」（用户亲手选增重/减重/保持 + 体重，只落这一行）；其余槽位全部由用户「添加目标」显式创建。下游消费方读不到行时回落 `GoalDefaults` 的机制**已具备**（如 `HealthAggregator.kt:164-165` 的 `?: GoalDefaults`），零消费方改动。首次引导 `GoalSetupSheet` 负责主目标的首次落库。

### 问题 3 · 计划按「天」为单位、按时间点穿插吃/练 —— 机制已有、体验不符

**现状（机制其实已在）**：

- `PlanGenerator` 本来就以**一天**为单位、按 `HH:mm` 时间点生成条目：`PROMPT_PLAN`（`PlanGenerator.kt:45-66`）要求「只排现在之后的时段、每项必须有 time、type ∈ meal/exercise/sleep/habit、按时间排序」；
- `TimelineMerger` 也确实把今日计划条目按 `sortKey = HH:mm` 插进了统一时间轴的今天格（`TimelineEntry.kt:123-139`）。

**与用户期望的差距**：

1. 只有**今天**那格有时间点条目；其余 6 天只有一条**无时间**的训练日行（`TimelineEntry.kt:107-121`，`sortKey=""` 排当天最前）→ 用户期望**每一天**都按时间点看到吃什么/练什么。
2. 感知层面：训练日行恒排最前，时间轴看起来像「周训练表」，计划条目像附属，感知不到「按时间点规划的一天」。

**修复方向（✅ 已拍板：方案 C —— 只细化今天 + 明天）**：

- **今天**：维持现状（`PROMPT_PLAN` 按时间点排当日吃/练，已上线）；
- **明天**：在同一次计划调用里顺带生成明天的早/午/晚 + 训练锚点（追加一组带 `day: 2` 的粗颗粒 items），**配额仍 1 行 `llm_calls`**（`PROMPT_VER_PLAN` 递增 v1→v2，prompt 加「明天」段）；
- **后天起**：维持一条无时间的训练日行（进到那天自然变「今天」，细排随之生成）；当天无计划时给「生成今日计划」入口。

对比候选：方案 A（一次生成整周 7 天时间点）未来天时间点纯估算、噪音大；方案 B（每天 1 次调用）7× `llm_calls` 违背整周一行架构。C 以零配额增幅覆盖用户真正会盯看的两天。

本地兜底（未配 Key）：`localTimeline` 同步补一组明天锚点（模板铺开，零网络）。

### 问题 4 · 记录页目标区占位过高 —— 从未覆盖

**现状**：`fragment_record.xml:59-206` 的目标区 = 主目标行（≈56dp）+ 目标宣言（0–2 行）+ 次目标块（标题 + 训练行 + **睡眠图 80dp** + **体重图 80dp** + 间距 ≈ 250dp），合计 ≈ **300–360dp**；叠加顶部输入区与「今日盈余」卡，目标相关内容约占 **半屏上下**。v8 需求 5 新增该区块时未做占位约束，属实。

**修复方向（原型已出，见 `docs/v8/UI-记录页目标区.html`）**：

- 压缩为「**一行主目标** + **一条 84dp 三卡横排**（训练进度 / 睡眠 / 体重，各含迷你 sparkline）」；
- 图表细节下沉：点任意卡 → 半屏详情弹层（大图 + 编辑入口）；
- 目标区总高 ≈ **140dp（< 20% 屏高）**，远优于「不到一半」的要求；
- 「今日盈余」卡同步压扁为单行摘要（点击进详情）。
