## 一、实现方案总述（含 A–F 裁定）

### 裁定 A：拼装落点与开关门控点 —— **采纳「ProfileContext 扩展」方案，外加两处 ui 层补拼**

- `repo/ProfileContext.build(db)` 扩展为：**硬约束段（原样）+ 软背景段（原样）+ 体格段 + 目标组段（含次目标行）**，整体受总开关 `AI_DATA_FULL` 门控（build 顶部读一次 settings，关 → 返回空串）。
  - ProfileContext 在 repo 层读 `settings` 与 `goals` 表均为 db 层依赖，**不违反分层**（goals 是 db 层，repo 可读）。
  - 消费点 `ChatViewModel:229` 与 `PlanGenerator:391` **零改动自动生效**（P0-3/4/6/8 一并满足；PlanGenerator 仅一处例外见裁定 F）。
- 「当前执行计划段」（P0-5，本周训练今天/明天那条 + 今日计划 note）依赖 ui 层 TrainingPlanner 与 daily_plans 解析 → **由 ChatViewModel 在 executeChat 内拼装**，追加进 background，受同一开关门控（经 `ProfileContext.aiDataFull(db)` 判定，该读点放 repo 层供三链复用）。
- 周训练链（P0-1）：`TrainingPlanner.buildUserContext` 自行追加「目标自述行 + ProfileContext.build(db) 整段」（同开关门控）。
- 门控读点唯一：`ProfileContext.aiDataFull(db)`，三链共用，无第二套判定。

### 裁定 B：TodaySummary 不扩展 —— **同意**

`lines` 同时喂 `ChatEngine.systemPrompt`、`HealthAgent.queryStats` 工具结果、`PlanGenerator.buildUserContext` 三处；扩段（体格/目标/次目标/计划）会放大每次工具调用的 token 且造成「工具结果里混入非记录数据」的职责漂移。体格/目标/次目标/计划走 background 注入，边界清晰、可独立门控。

### 裁定 C：键名与 UI —— **采纳，微调 toggle 方法**

- 键：`SettingsKeys.AI_DATA_FULL = "ai_data_full"`，取值 `"true"`/`"false"`，**键不存在 = 开（默认 true）**。判定口径唯一写法：`!= "false"`，禁止 `== "true"`（键缺失语义靠前者成立）。
- UI：设置页「热量摄入」组之后、「提醒」组之前新增组「AI 可见资料范围」，include `row_setting_switch`，id `rowAiDataSwitch`。开关语义**不取反**（与 hideKcal 的「隐藏取反显示」不同：checked = aiDataFull 本身）。
- SettingsViewModel：新增专用方法 `toggleAiDataFull()`（镜像 toggleHide 写法）；**不动 `toggleHide`**（其 KDoc「key 只允许 HIDE_*」的约束保持成立，避免语义扩散）。

### 裁定 D：周训练 prompt v2 与 buildUserContext 新增行

- PROMPT_TRAINING v1→v2：在硬规则 1 与原规则 2（生病）之间**插入两条**（疼痛避让、运动条件遵守），原 2–6 顺延为 4–8；「输出要求」「输出格式」两段**一字不动**。全文见第五节，工程须在 `ui/TrainingPlanner.kt` 与 `pipeline/contract.py` 两处**逐字节落同一份**，两文件 `PROMPT_VER_TRAINING` 同步 `"v2"`（CI check_prompt_parity + 版本常量存在性校验）。
- 画像为空/开关关闭的行为：新规则 2/3 内嵌「画像未提供时跳过本条」，模型侧自洽；拼装侧 `ProfileContext.build` 返回空串则整段省略，不给模型空标头。
- buildUserContext 新增行（插在「今日睡眠」行之后、「请排出…」行之前）：
  1. `目标自述：${GOAL_STATEMENT}`（非空才出，且受开关门控）
  2. 空行 + `ProfileContext.build(db)` 整段（硬约束/软背景/体格/目标/次目标，开关关闭时空串省略）

### 裁定 E：对话链 background 拼装顺序与标头措辞

顺序（受总开关统一门控；空段整段省略）：

```
【硬约束——必须遵守】            ← 原样，语义不动（忌口/疼痛=行为约束）
就餐场景：…／作息：…／手头…／常备药物…／自由文本   ← 原软背景段，原样
【体格资料（来自个人资料设置与体重记录，事实参考）】  ← 新增，事实参考类
【目标（来自目标设置，仅列出已设置项）】             ← 新增，含自定义次目标行
【当前执行计划（本地生成的计划，事实参考）】          ← 新增，仅对话链（ChatViewModel 拼装）
```

**措辞失真评估（systemPrompt 标头「用户自己写的，视为可信前提」）**：可接受。理由：① 模板字节冻结，无改标头路径；② 段内标头自带来源括注（「来自目标设置」「来自…记录」），模型对「可信前提 + 来源标注」的组合不会产生行为歧义（把目标数字当可信上下文正是本需求意图）；③ 硬约束段「必须遵守」与事实段「事实参考」的强度差通过括注词区分（「必须遵守」vs「事实参考」），与硬边界 2 的呼应关系不破坏。

### 裁定 F：今日计划链口径 —— **保持现状（兜底值合法），仅一处门控修正**

- 今日计划链的「每日目标摄入 / 每周训练 / 睡眠目标」行是**排程操作数**（排计划必须有可执行数字），与对话链「引用用户目标」语境不同 → **保留 GoalDefaults 兜底，不改口径**（与主理人 Q 裁定精神一致）。
- 唯一修正：`PlanGenerator.buildUserContext` 的「目标（用户自述）」行是**画像类自由文本**，P0-7 关闭时必须随之消失 → 该行加 `ProfileContext.aiDataFull(db)` 门控（关闭时整行省略，不打印「未填写」）。其余行不动。
- P0-8（计划链补体格/次目标）由 ProfileContext 扩展零改动自动生效，无需另写。

### 其它裁定

- **PROMPT_VER_CHAT v1→v2**：background 通道内容变化 = systemPrompt 实际内容变化，按 ChatEngine KDoc 既定协议递增；模板字节不动（ChatEngine.kt 只改常量一行）。
- **对话链「今天/明天」训练行口径**：本周计划存在且当天是休息日 → 输出「休息」（休息日本身是有信息量的事实）；本周计划不存在 → 省略该行。与 PlanGenerator 的 `null→"无"` 口径刻意不同（对话链遵循「空则省略」先例）。
- **hide_weight 在体格段的落法**：体重行读 `events(type=body)` 最近一条（`weightRowsInRange` 近 365 天，与 SettingsViewModel「当前体重」行同口径）；`hide_weight=true` 时**整行省略**（沿用 TodaySummary「整行省略、不写已隐藏」先例）。

### 3.4 ChatViewModel（ui/ChatViewModel.kt）

```kotlin
// executeChat 内（现 :229 处之后）：
val background0 = ProfileContext.build(db)
val planSection = buildPlanSection()
val background = listOf(background0, planSection).filter { it.isNotBlank() }.joinToString("\n\n")

/** P0-5/P0-7：当前执行计划段。总开关关闭或三条全空 → ""（整段省略）。 */
private suspend fun buildPlanSection(): String {
    if (!ProfileContext.aiDataFull(db)) return ""
    val today = com.healix.app.ui.trainingPlanLineFor(getApplication(), 0)
    val tomorrow = com.healix.app.ui.trainingPlanLineFor(getApplication(), 1)
    val note = todayPlanNote()
    if (today == null && tomorrow == null && note == null) return ""
    return buildString {
        appendLine("【当前执行计划（本地生成的计划，事实参考）】")
        today?.let { appendLine("- 本周训练·今天：$it") }
        tomorrow?.let { appendLine("- 本周训练·明天：$it") }
        note?.let { appendLine("- 今日计划备注：$it") }
    }.trim()
}

/** 今日计划备注：daily_plans.planJson 的 note 字段。防御式解析，异常/null → null。 */
private suspend fun todayPlanNote(): String? {
    val row = runCatching { db.planDao().getPlan(todayKey()) }.getOrNull() ?: return null
    val json = row.planJson ?: return null
    val obj = runCatching { com.healix.app.parse.loadsLenient(json) }.getOrNull()
        as? org.json.JSONObject ?: return null
    // ⚠️ 用 opt() 而非 optString()：optString 对 JSON null 返回字面 "null"
    //    （PlanGenerator.parseTimelineJson 同款坑）。取原生 String 才安全。
    return (obj.opt("note") as? String)?.trim()?.takeIf { it.isNotEmpty() }
}
```

## 四、PROMPT_TRAINING v2 全文（两处逐字节落盘：`ui/TrainingPlanner.kt` 与 `pipeline/contract.py`）

```text
你是 Healix 的训练计划助手。根据用户的目标、本周已练肌群与恢复度，排出本周（周一至周日）7 天的训练安排。

硬规则（逐条遵守，冲突时序号小的优先）：
1. 结合「本周已练肌群」与「恢复度摘要」：同一肌群 48 小时内不重复安排；恢复度低于 50% 的肌群本周内不再安排。
2. 若用户画像给出疼痛/不适部位：不安排刺激该部位的动作，该部位当天以恢复为主，可给不涉及该部位的替代动作；画像未提供疼痛信息时跳过本条。
3. 若用户画像给出忌口或运动条件（器材/场地/时段）：动作只能使用可用器材与场地，时段约束必须遵守；画像未提供时跳过本条。
4. 若今日或昨日有生病记录 → 不安排任何训练，整周改为休息 + 补水 + 睡眠的安排。
5. 若今日睡眠不足 6 小时 → 当天训练降低强度：每个动作减 1 组，或改为轻量有氧。
6. 若本周训练次数已达到每周目标 → 多排休息日，不硬凑；绝不允许为了凑够次数而额外加练。
7. 组次区间按目标给：增肌 每组 6-12 次；力量 每组 1-5 次；保持体能 每组 12-20 次。
8. 禁止输出 1RM 估算、力量总分、综合评分或任何形式的打分。

输出要求：
- 只输出 JSON，不要任何解释文字，不要 markdown 代码围栏。
- days 恰好 7 条，dow 依次为 1..7（1=周一，7=周日）。
- 训练日 title 写部位/主题（如「推（胸/肩/三头）」），items 给 2-4 个动作，每个动作含 name / sets / reps，reps 用区间字符串（如 "8-10"）。
- 休息日 title 固定写「休息」，items 为空数组 []。
- focus 一句话概括本周重点；note 一句话提醒用户（可涉及恢复、睡眠或目标）。

输出格式固定为：
```

## 五、关键调用流程（文字时序）

### 5.1 对话链注入链路

```
用户发消息
 → ChatViewModel.executeChat（IO 协程；配额/配置/断网前置检查不变）
 → knowledgeRepository.search(text)（不变）
 → background0 = ProfileContext.build(db)
     ├─ ProfileContext.aiDataFull(db) == false → 返回 ""（画像/体格/目标/次目标全不注入）
     └─ true → 硬约束段（原样）+ 软背景段（原样）+ 体格段（hideWeight 过滤体重行）
              + 目标组段（缺失项省略；含 CUSTOM_GOAL_TEXT 次目标行）
 → planSection = buildPlanSection()
     ├─ aiDataFull == false → ""
     └─ true → trainingPlanLineFor(ctx,0/1)（TrainingPlanner.loadOrGenerate(false) 纯读缓存，绝不触网）
             + todayPlanNote()（db.planDao().getPlan(todayKey()) 解析 planJson.note）
 → background = [background0, planSection] 非空 joinToString("\n\n")
 → HealthAgent.run(background=background)（systemPrompt 同源 + TOOLS_SECTION）
     └─ 失败回退 ChatEngine.reply(background=background)（同一值，既有路径不动）
 → llm_calls 落一行，prompt_ver = PROMPT_VER_CHAT（"v2"）
```

注：`ChatEngine.systemPrompt` 模板字节不变——全部新数据经 background 参数注入，与知识库段同一通道。

### 5.2 周训练链

```
用户点「生成本周计划」（force=true；本周已缓存则不触发）
 → TrainingPlanner.generate → tryAi
 → buildUserContext()：
     原有行（本周目标/周次数/已练肌群/恢复度/生病/今日睡眠）
     + 「目标自述：…」（GOAL_STATEMENT 非空且 aiDataFull）
     + ProfileContext.build(db) 整段（aiDataFull 门控；含硬约束/软背景/体格/目标/次目标）
 → system = PROMPT_TRAINING（v2，与 contract.py 逐字节一致）
 → 一次 provider 往返 → llm_calls 一行 prompt_ver="v2"
```

### 5.3 开关切换生效链路

```
设置页 rowAiDataSwitch 拨动（或整行点击）
 → SettingsViewModel.toggleAiDataFull()（IO）
 → settings.put("ai_data_full", "true"/"false") → reload() → values 回填（先摘监听防写回环）
 → 三链下一次调用 ProfileContext.aiDataFull 现读 settings → 立即生效（无缓存、无需重启）
 → hide_kcal / hide_weight 与工具（query_events/query_stats/propose_log）不受影响（裁定 Q1）
```

## 七、共享约定（工程必读）

1. **开关判定唯一口径**：`!= "false"`（键不存在 = 开）。全仓禁止出现 `== "true"` 判 AI_DATA_FULL 的写法。读点唯一：`ProfileContext.aiDataFull(db)`；设置页回填用同口径读 `SettingsValues.aiDataFull`。
2. **空则省略**：任何段/行无数据 → 整段/整行不出现，不留空标头、不写「未记录」以外的占位（沿用既有先例）。
3. **段标头自带来源括注**：「必须遵守」（硬约束）vs「事实参考」（体格/目标/计划），强度差靠措辞不靠模板。
4. **prompt 字节纪律**：PROMPT_TRAINING v2 两处逐字节；PROMPT_VER_TRAINING 两处同步 "v2"；PROMPT_VER_CHAT → "v2"；PROMPT_EXTRACT / PROMPT_PLAN / ChatEngine.systemPrompt 模板零触碰。
5. **settings 键纪律**：`ai_data_full` 字面量只出现在 SettingsKeys.kt（check_settings_keys 强制）；不新增 GoalDefaults 值；`CUSTOM_GOAL_TEXT` 自本轮起合法进入 AI 读取集合（三链统一），KDoc 同步修订。
6. **静态检查器盲区规避**：suspend 转发一律块体 `{ return … }` 禁 `= expr`（aiDataFull、todayPlanNote 等新挂起函数按 3.2/3.4 签名的块体写）；非 suspend 函数体禁直调挂起方法（本设计所有新读取都在既有 suspend 协程内）；跨文件引用一律限定 `ProfileContext.` / `SettingsKeys.`（check_object_scope）；新增 const `AI_DATA_FULL` 全仓唯一（check_duplicate_constants 判据=同名且同值）；无 fragment-ktx，VM/Fragment 模式照旧。
7. **日界线纪律**：`todayPlanNote` 的日期键必经 ChatViewModel 既有 `todayKey()`（内部 dayStartHourOf + dayKeyOf），不得 `LocalDate.now()` 直拼。
8. **成本纪律**：`trainingPlanLineFor` 只允许 `loadOrGenerate(force=false)` 纯读缓存路径，绝不触发模型调用；一次 provider 往返仍恰好一行 llm_calls，不新增调用点。
