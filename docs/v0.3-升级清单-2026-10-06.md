## 1. 计划页滑动弹跳

### 现状问题

**取证**

| 位置 | 事实 |
|------|------|
| `fragment_plan_review.xml:116-121` | 滚动容器是 `ScrollView#contentScroll`，唯一子节点是一个 `LinearLayout` |
| `fragment_plan_review.xml:220-224` | 时间轴条目容器 `itemContainer` = 普通 `LinearLayout`（无回收） |
| `PlanReviewFragment.kt:228-229` | `renderTimeline()` **每次调用先 `itemContainer.removeAllViews()`** |
| `PlanReviewFragment.kt:251-254` | 再逐条 `addView(dayHeader/entryRow)` 全量重建 |
| `PlanReviewFragment.kt:100-109` | `renderTimeline` 由 `vm.plan.collect` 驱动 —— 每次 StateFlow 发射都重建 |
| `PlanReviewViewModel.kt:252-269` | `computeAndEmit()` 每次 `_plan.value = copy(...)` 都发射 |
| `PlanReviewViewModel.kt:183-190` | 发射源之一是 Room Flow `observeCountByDay(key)` —— **记一笔 / 后台任何写入都会触发** |
| `PlanReviewFragment.kt:232-244,257-258,177,153,183-197` | 同帧内还有 6+ 处 `visibility` 切换（`planEmptyRow`/`planNote`/`planModeLabel`/`planSourceLabel`/`trainingSummary`/`trainingGenerateRow`） |
| `PlanReviewFragment.kt:138` | 撤销条出现时调 `contentScroll.smoothScrollTo(0, 0)` |

**根因（一句话）**：`ScrollView` 在 `onLayout` 会把 `scrollY` 夹取到 `[0, contentHeight - viewportHeight]`。全量重建（`removeAllViews` → 逐条 `addView`）与多处 `visibility` 切换会让内容高度在同帧内**先塌陷后恢复**；用户此时若 scrollY 已接近顶部，夹取结果就是 `0` 且**不会被还原** → 表现为"弹一下并直接跳到顶部"。

**为什么"接近顶部"最明显**：内容塌陷幅度越大，被夹取到的值越小；scrollY 本身小的时候，夹取到 0 的视觉落差最突兀（顶部边缘直接贴齐）。

### 优化目标

- 滑动过程零位置跳变；数据更新时**保持当前滚动位置**（scrollY 变化 = 0）。
- 顺带消除全量重建带来的列表规模开销。

### 方案（推荐 A，B 为兜底必做）

| 方案 | 做法 | 评价 |
|------|------|------|
| **A（推荐）** | `itemContainer` 换 `RecyclerView` + `ListAdapter`/`DiffUtil`（`item_plan_timeline.xml` 原样复用）；滚动位置由 RecyclerView 自身持有 | 根治；性能随条目数线性改善。依赖已有（记录页在用 RecyclerView，无需新依赖；**不需要 fragment-ktx**） |
| **B（兜底，必做）** | 保留 ScrollView：重建前 `val y = contentScroll.scrollY`，重建后 `contentScroll.post { scrollTo(0, y) }`；并把所有 `visibility` 变更**合并到重建末尾一次完成**，消除中间态 | 改动最小；仍付全量重建成本 |
| C（不推荐） | 只去掉 `smoothScrollTo` / 加 `descendantFocusability` | 治标不治本 |

> 注：`smoothScrollTo(0, 0)`（`:138`）本身是刻意设计（保证撤销条可见，PRD §15.7），**不要直接删**；A 方案下改为"仅当目标不可见时才滚动"。

### 验收标准

1. 真机：计划页任意位置连续上下滑动 10 次，**不出现位置跳变**；
2. 在页面中部停留时触发一次数据变化（记录页记一笔）→ 计划页 scrollY 前后相同（自动化或 `PerfProbe` 打点核对）；
3. 条目 ≥ 30 条时，`nav.open → frag.resumed` 与渲染总耗时**不高于**改前（用 `PerfProbe` MARK 对照 `docs/v8/专项-二级页转场卡顿-2026-10-05.md` 基线）；
4. 空态（`planEmptyRow`）与有内容态来回切换 5 次，无跳顶。

### 影响范围

`res/layout/fragment_plan_review.xml`、`PlanReviewFragment.renderTimeline/dayHeader/entryRow`、新增 Adapter（若走 A）。
**不触碰**：`PlanReviewViewModel`、AI 链路（打开页面 0 AI 的不变式保持）、`TimelineMerger`。

## 2. 记录页合并滚动区

### 现状问题

`fragment_record.xml` 根节点是 `LinearLayout(vertical)`，**非滚动固定区**：

| 区块 | 行号 | 高度 |
|------|------|------|
| 日期栏 + 设置按钮 | `:20-45` | 56dp + 1dp 线 |
| 目标区 `goalArea` | `:59-335` | ≈142dp（注释自述，`:53-56`） |
| 预设横条 `presetScroll` | `:338-354` | 48dp（可隐藏） |
| 多维状态行 `statusRow` | `:377-407` | 48dp |
| 监督提示条 / 计划提示条 | `:410-433` | 48dp × 0–2 |
| 状态提示条 / 撤销条 | `:441-492` | 0–48dp × 2 |
| **只读列表** `RecyclerView#list` | `:495-506` | `layout_weight=1`（唯一滚动区） |
| 输入条 `inputBar` | `:538-591` | 64dp（**刻意不参与滚动**，`:533-537` 注释说明抬升与 IME 逻辑） |

**问题**：约 **300–350dp 恒不滚动**（≈屏高 35–40%），手指落在目标卡片/状态行上滑动时页面不动 → 明确的"分区割裂感"。

### 优化目标

- 顶部信息随内容上滑离场，整页单一滚动轴；
- 输入条**保持固定**（打开即记的核心入口，不能滚走），列表末尾不被遮挡。

### 方案（推荐 A）

| 方案 | 做法 | 评价 |
|------|------|------|
| **A（推荐）** | `RecyclerView` 多 ViewType：把 `goalArea` / `presetScroll` / `statusRow` / 各提示条做成 header item type（或 `ConcatAdapter` 拼接）；事件行沿用现有 `EventAdapter` | 性能最优、复用已有回收机制；header 数量固定，DiffUtil 开销可忽略 |
| B | `NestedScrollView` 包全部 + 内层 `RecyclerView` 设 `nestedScrollingEnabled=false` 并按内容测量高度 | 改动快，但内层列表**失去回收**，记录上百条时会掉帧 —— 只可作临时验证 |
| C | 自绘 `NestedScrollingChild` | 成本过高，不考虑 |

**必须一并迁移的三处**（漏一处即功能回归）：

| 现有实现 | 行号 | 迁移要点 |
|---|---|---|
| `SwipeController` + `addOnItemTouchListener`（左滑删/点外回弹） | `RecordFragment.kt:106-115,172-186` | 手势判定本就是基于**子 View 坐标**，RecyclerView 内仍成立；但 `binding.root.setOnTouchListener`（`:183-186`，收起滑开行）在 header 上也要生效 → 改挂到 RecyclerView |
| `InputBarHeightAnimator` 回调里 `smoothScrollToPosition(last)` | `:199-202` | position 需按 header 数量偏移 |
| 空态覆盖层 `emptyState` | `fragment_record.xml:509-530` | 改为"列表为空时插入一条空态 item"或保留 FrameLayout 覆盖层（推荐后者，零风险） |

### 验收标准

1. 手指落在**目标卡片区 / 状态行 / 提示条**上滑动 → 页面跟随滚动，无死区；
2. 顶部区块完全离场后，列表仍可继续滑到底部，末条不被输入条遮挡（`clipToPadding=false` + `paddingBottom` 已具备，`:504-505`）；
3. 键盘弹出 → 输入条贴键盘顶、列表随之上移（`bindImeGuard` 语义不变）；
4. 点击回归：`goalPrimaryRow` / `subTrainRow` / `subSleepRow` / `subWeightRow` / `gapRow` / `statusRow` / `planBar` / `nudgeBar` / 离线条 全部行为与改前一致；
5. 记录 100 条时滑动帧率不低于改前。

### 影响范围

`fragment_record.xml`（重构）、`RecordFragment`（binding/adapter/touch）、`EventAdapter`、`SwipeController` 挂载点、`InputBarHeightAnimator` 调用点。
**风险等级：高**（记录页是主入口，且是「打开即记」路径）→ 独立成批、真机回归后再合。

## 3. 设置新增「规则库」

### 现状问题

**没有规则库**。AI 输出规则**硬编码**在系统提示里：

| 位置 | 事实 |
|------|------|
| `ChatEngine.kt:247-263` | 输出规则 = 「说话方式」段（一整段长中文）+「硬边界」4 条 + 隐私追加项 |
| `ChatEngine.kt:23` | `PROMPT_VER_CHAT = "v2"`；该函数**字节冻结**（`PROMPT_PARITY` 强制字节同步） |
| `fragment_settings.xml:105-417` | 分组：模型服务 / 调用限制 / 目标 / 热量摄入 / **AI 数据**（`:372-380`）/ 提醒 —— 无规则入口 |
| `SettingsFragment.kt:1123-1140` | 无规则相关处理 |

**"输出过多 + 上下文重复"的根因（四处，可逐条取证）**：

1. **同一份数据进两次**：系统提示注入 `TodaySummary.build(context).lines`（`ChatEngine.kt:199-200`）作为"今天的已知数字"；而 agent 又提供 `query_stats` 工具（`HealthAgent.kt:97-107`），其实现**返回同一份 `TodaySummary.build(context).lines`**（`HealthAgent.kt:186`）→ 模型可能同时看到两遍今日数字。
2. **历史无压缩**：`HISTORY_WINDOW = 16`（`ChatEngine.kt:280` / `HealthAgent.kt:373`），每轮全量重发，无摘要、无截断策略。
3. **background 通道体量大**：`ProfileContext.build()` 输出 4 段（硬约束 / 软背景 / 体格 / 目标组，`ProfileContext.kt:74-181`），其中「目标组段」（`:159-180`）与 `TodaySummary` 的 `primaryGoalName`（`ChatEngine.kt:248`）**语义重叠**。
4. **规则不可调**：说话方式段 + 4 条硬边界恒量存在，用户无法表达"回答短一点""不要分点""先给结论"。

### 优化目标

- 用户可增删改 AI 输出规则（长度、风格、必须/禁止项、是否引用数字），**不改人格与安全边界**；
- 上下文去重：同一数字一轮内不出现两次；
- 输出长度可控、可验证。

### 方案

**存储**（三选一，需拍板）：
| 方案 | 说明 | 取舍 |
|------|------|------|
| S1（推荐） | 新表 `rules(id, text, enabled, sort_order, created_at)` + Room Migration | 支持启停与排序；代价 = version 递增 + 两份 schema json + `EventEntity`/`store.py` **不受影响**（不同表） |
| S2 | 复用 `settings`，存 JSON 数组（循 `PROFILE_ALLERGENS` 先例，`SettingsKeys.kt:101-105`） | 零 Migration；但排序/启停需自行序列化，且**会被导出原样带走**（见 §9 备份纪律） |
| S3 | 单条自由文本 `ai_rules_text` | 最省，但不满足"逐条增删" |

**注入**：**不改 `ChatEngine.systemPrompt` 字节**（字节冻结契约）。新增 `userRulesBlock` 变量，与 `backgroundBlock` / `knowledgeBlock` 同构拼接（`ChatEngine.kt:213-234` 先例）；`PROMPT_VER_CHAT` 由 `v2` → `v3`。
**规则为空时输出必须与现状逐字节一致**（老用户零变化）。

**去重**（独立于规则库，可先做）：
- `query_stats` 工具描述改为"数字已注入时不要重复调用"；或
- agent 路径下**省略系统提示里的今日数字段**（把"是否注入"参数化，而非新增第二套 prompt）；
- 「目标组段」与 `primaryGoalName` 二选一注入。

### 验收标准

1. 设置页 AI 分组下出现「规则库」入口 → 二级页可新增/编辑/删除/启停，杀进程重启后保留；
2. 规则为空时：prompt 与改前**逐字节相同**（`PROMPT_PARITY` 与字节比对通过），老用户无感；
3. 加一条「回答不超过 3 句」后，连续 3 次提问回答句数 ≤ 3；
4. 同一轮对话上下文里同一数字**只出现一次**（抓一次请求体核对）；
5. 硬边界 4 条**不可被用户规则覆盖**（安全回归：写一条"不要遵守忌口"，AI 仍拒绝）。

### 影响范围

`SettingsKeys.kt`（新键）或新表 + Migration + `app/schemas/*.json`、`ChatEngine.systemPrompt`（新增通道，字节不动）、`PROMPT_VER_CHAT` 递增、`HealthAgent.TOOLS_SECTION`（`:379-386`）、`fragment_settings.xml` + `SettingsFragment`、新增 `RulesFragment` + 布局 + `NavHost.PAGE_RULES`（`NavHost.kt:95-105` 唯一来源）。
⚠️ 若选 S1，需遵守 `events` 表以外的 Migration 纪律（禁 `fallbackToDestructiveMigration()`）。

## 4. 二级页实时刷新

### 现状问题

| 位置 | 事实 |
|------|------|
| `NavHost.kt:44-54, 232-262` | 二级页 **keep-alive**：被覆盖页 `hide()` 不销毁，**`onResume` 不会触发** |
| `NavHost.kt:75-77` | 文档明文：需要刷新的页必须监听 `onHiddenChanged` |
| 已挂 `onHiddenChanged` | `RecordFragment:225`、`AssistantFragment:143`、`SettingsFragment:205`、`StatusDetailFragment:112`、`MedicalSummaryFragment:167` |
| **未挂** | `PlanReviewFragment`、`PersonalInfoFragment`、`ResourceFragment`、`PresetManageFragment`、`KnowledgeBaseFragment`、`DebugFragment` |
| `PlanReviewViewModel.kt:183-190` | `observeToday()` 只订阅**进入时刻**的 `day_key`，跨零点后该键过期；init 后不再 reload |

**表现**：在二级页 A 停留 → 进 B 改数据 → 返回 A，A 仍显示旧快照，必须退出重进。

### 优化目标

任一二级页被覆盖后返回时，展示数据与"重新进入"一致新鲜；跨零点返回后日期口径正确。

### 方案

1. **统一范式（推荐）**：在 `NavHost` 层加"页面可见"回调（`onPageShown(tag)`），或在 `NavHost` 提供 `PageFragment` 基类 —— 从结构上杜绝"某页忘挂"。**优先级高于逐页补**。
2. 逐页补 `onHiddenChanged(false) → refresh()`（6 个页面，纯加法）；
3. 刷新语义分级（写进文档，避免后人乱挂）：
   - **Room Flow 订阅** = 天然实时（`MineFragment.homeStatus`、`PlanReviewViewModel.observeToday`）；
   - **`onHiddenChanged(false)` 重建读取** = 跨零点 / 外部变更兜底；
   - **`onResume`** = 二级页**不用**（keep-alive 下不触发）。
4. `PlanReviewFragment`：`onHiddenChanged(false)` 时 `vm.reload()` + 重订阅今日 key。

### 验收标准

逐页回归表（每页给出可核对字段）：

| 页面 | 触发动作 | 期望 |
|------|---------|------|
| 计划页 | 设置页改目标 → 返回 | 缺口行 / 时间轴 / 训练汇总同步 |
| 个人信息页 | 记录页记体重 → 返回 | 最新体重刷新 |
| 资源清单页 | 修改手头食物 → 返回 | 列表刷新 |
| 预设管理页 | 记录页用预设 → 返回 | 使用计数/排序刷新 |
| 知识库页 | 删除文档 → 返回 | 列表刷新 |
| 全部 | 系统时间 03:59 → 04:01 返回 | 日期标签与列表**同口径**（日界线纪律） |

### 影响范围

6 个 Fragment（纯加法）、`NavHost`（可选钩子）、`PlanReviewViewModel`（reload 时机）。
**风险低**；唯一红线 = 不得用 `onResume` 替代。

## 5. AI 操作用户数据 + 开关

### 现状问题

| 位置 | 事实 |
|------|------|
| `HealthAgent.kt:66-125` | `ToolRegistry` 只有 3 个工具：`query_events` / `query_stats`（只读）、`propose_log`（拟稿） |
| `HealthAgent.kt:26-29, 192` | **明确边界**："Agent 自身无权直接写入 events 表" |
| 缺口 | **没有任何"计划/目标"相关工具** —— AI 无法改今日计划、周训练、目标值 |
| `SettingsKeys.kt:155` | 唯一相关开关是 `AI_DATA_FULL`（**读范围**总开关），**无工具/写权限开关** |
| `HealthAgent.kt:328-360` | `llm_calls` 只记 `prompt_ver`/`status`/耗时/用量；**不记工具名、参数、结果** |
| `HealthAgent.kt:41, 286` | `toolsUsed` 只回传给 UI 气泡角标，不落库 → 无审计 |
| `HealthAgent.kt:151-154` | 参数校验仅 `query_events` 有日期正则；写类工具（新增）**必须**补白名单校验 |

### 优化目标

- AI 能（**在用户确认下**）操作计划与记录；
- 权限可控、可审计；写操作**永不自动执行**。

### 方案（对齐行业分层：只读 → 拟稿 → 受监督写入 → 窄自主）

**行业共识**（2026 检索）：先只读，再拟稿，再受监督写入，最后才窄自主；写操作必须 two-step（AI 提议 → 用户确认 → 执行）。已有事故先例：AI 把"如果加到 7mg 会怎样"这个**假设性问题**当成指令直接改了处方。

**Step 1 — 只读工具（低风险，先做）**
| 工具 | 用途 |
|------|------|
| `query_plan(day/range)` | 查今日/本周计划条目 |
| `query_goal()` | 查目标组当前值 |
| `query_training_week()` | 查本周训练安排与完成情况 |

**Step 2 — 拟稿工具（人工确认后执行）**
| 工具 | 用途 | 落库路径 |
|------|------|---------|
| `propose_plan_change` | 加/改/删今日或周计划条目 | 复用 `ActionConfirmSheet`（已存在）→ `PlanReviewViewModel` |
| `propose_goal_change` | 改目标值 | `GoalDao` + `goals` 表 |
| `propose_record_delete` | 删记录 | `EventRepository` 软删（复用 UndoBar） |

**实现约束（硬）**：
- 所有写工具**只产 draft**，与 `LogProposal`（`HealthAgent.kt:31`）同构；UI 确认后才落库；
- `ProposalPending` 分支（`:309-313`）已实现"拟稿即终止循环"—— 新工具沿用同一分支；
- 提示词必须**显式声明当前权限**（"你当前只有只读权限"），不能只靠 UI 拦。

**开关（设置页 AI 组，`fragment_settings.xml:372-380` 下方）**
| 键（建议名） | 默认 | 语义 |
|---|---|---|
| `AI_TOOLS_ENABLED` | 开 | 关 = 退回单轮 `ChatEngine`（即现有降级链第二级） |
| `AI_TOOL_WRITE_PLAN` | 关 | 允许拟稿改计划 |
| `AI_TOOL_WRITE_RECORD` | 关 | 允许拟稿删/补记录 |
| `AI_TOOL_WRITE_GOAL` | 关 | 允许拟稿改目标 |

⚠️ 与 `AI_DATA_FULL` 的关系需**拍板**：现状该开关**不影响工具**（`ProfileContext` 只门控注入，工具照常查库）—— 是否改为"总开关关闭时工具也禁用"需明确。

**可观测（建议同批做）**：新增 `tool_calls` 表记 `name / args / result 摘要 / 耗时 / 是否需确认 / 用户是否批准`；或在 `llm_calls` 加 `tools_used`（需 Room version + Migration）。

### 验收标准

1. `AI_TOOLS_ENABLED = 关` → 提问无工具角标，`llm_calls` 恰好 1 行（单轮路径）；
2. 开 `AI_TOOL_WRITE_PLAN` 后说"把今天下午的训练改成休息" → **弹确认** → 确认后计划页时间轴该条变化；拒绝则无变化；
3. 未开权限时，即使模型构造了写调用，系统也**拒绝执行**并回一句说明（不能只靠 UI）；
4. 每次工具调用可在 `tool_calls`/日志中查到 name、args、批准状态；
5. 写工具的参数校验：非法时间格式 / 越界目标值 → 返回错误文本，**不抛异常**（循 `:133-145` 先例）；
6. 配额不变式：一次 provider 往返**恰好 1 行** `llm_calls`（现有纪律不被破坏）。

### 影响范围

`agent/HealthAgent.kt`、`ChatViewModel`、`SettingsKeys` + `fragment_settings.xml` + `SettingsFragment`、Room（新表或新列 + Migration + schema json）、`ActionConfirmSheet.kt`、`PlanReviewViewModel` / `GoalDao`（新写入路径）。
**建议分两批**：Step 1 只读工具（可独立交付）→ Step 2 写工具（含确认 UI + 审计）。

### 6.2 Healix 差距表

| 维度 | Healix 现状（取证） | 成熟软件 | 差距 |
|------|-------------------|---------|------|
| 数据源广度 | 仅本地 SQLite 记录（`ToolRegistry` 3 工具） | EHR + 可穿戴 + 第三方 App | **结构性**（自用定位，可接受） |

| Agent 架构 | 有界循环：4 步 / 30s / 同参即停（`HealthAgent.kt:362-370`） | 长程 agent + 推理交织工具调用 | **大**（自用约束） |
| 模型能力 | 用户自配（免费档 flash 类），`temperature=0.7` | 专用健康模型 + 医学审校 | **大**（成本约束） |
| 上下文效率 | 今日数字重复注入 + 历史 16 条无摘要 | 独立记忆库 + 会话摘要 + 检索式上下文 | **中** → 需求 3 |
| 安全/隐私 | 本地 SQLite、API key 不进 settings、隐私开关、**导出无第二道闸门** | 沙箱隔离、不用于训练、身份核验 | **中**（本地存储反而更优） |
| 可观测 | `llm_calls` 无工具明细 | 工具名/参数/结果/审批全链路 trace | **大** → 需求 5 |
| 交互入口 | 速记框 + 对话 + 桌面小工具 | 语音 / 拍照 / 可穿戴自动写入 | **中** |

### 6.3 「AI 接入后表现明显下降」根因诊断

| # | 根因 | 取证 | 影响 |
|---|------|------|------|
| 1 | 系统提示显著变长：`ChatEngine.systemPrompt`（persona + 长段说话方式 + 4 条硬边界）+ `TOOLS_SECTION` 拼接 | `HealthAgent.kt:240-244, 379-386` | 弱模型在"人格遵循"与"工具选择"间竞争注意力 |
| 2 | 工具调用温度偏高 | `HealthAgent.kt:266` `temperature = 0.7` | 工具参数需稳定，0.7 易产生格式偏差 |
| 3 | 免费档 flash 类模型 tool-calling 能力弱 | 用户自配 provider | 检索结论：**参数微小偏差会沿工具链传播失败** |
| 4 | 循环预算紧：4 步 / 30s / 单次 12s | `HealthAgent.kt:364-370` | 复杂问题直接 `Failed` → 回退单轮 → 用户感知"变笨了" |
| 5 | 回退仍耗配额：每次 provider 往返都记一行 | `HealthAgent.kt:328-360` | 达到日限后**只能降级**，雪上加霜 |
| 6 | 无工具结果缓存 | 每次 `query_events` 都查库 | 同问题重复查，浪费往返 |

**结论**：这不是"模型变笨"，而是 **Agent 路径的提示组织、采样参数、预算与配额交互**共同劣化。优先修 1/2/4 三项（零架构成本）。

### 6.4 优化方向

| 项 | 动作 | 优先级 |
|---|------|--------|
| A | 工具模式用**精简系统提示**（保留硬边界 + 工具段，压缩说话方式段）；或按路径参数化注入 | P0 |
| B | 工具路径 `temperature` 降至 0.3–0.5 | P0 |
| C | 核对回退链埋点是否**移位记录**（一次往返恰好一行，禁补记） | P0 |
| D | 提高 `MAX_STEPS` 或放宽墙钟（需与配额纪律权衡） | P1 |
| E | 工具结果短时缓存（同参 5 分钟） | P1 |
| F | 长对话摘要（每 N 轮压缩一段） | P1 |
| G | 工具描述收紧（描述是可靠性关键，但**工具越多越混乱**，控制总数） | P1 |

### 验收标准

1. 给出一份"改前/改后"对照：同一组 10 个问题（含需查证类、需工具类、闲聊类），记录 **首次回答命中率 / 平均往返次数 / 平均耗时**；
2. `Failed` 回退率（agent → 单轮）下降 ≥ 30%；
3. 配额不变式保持：一次往返恰好一行 `llm_calls`。

### 影响范围

`HealthAgent`（提示组织、采样参数）、`ChatEngine.systemPrompt`（参数化，字节不动）、埋点核对（`EventRepository.recordChatCall`）。

### 8.2 跨需求红线（改前必读）

1. **不改字节冻结区**：`PROMPT_EXTRACT` / `ChatEngine.systemPrompt` / `TrainingPlanner.PROMPT_TRAINING` / `pipeline/contract.py` 与 `parse/SchemaValidator.kt` 契约。新增内容走**新通道**，版本号各自递增。
2. **配额不变式**：一次 provider 往返**恰好一行** `llm_calls`；失败也记，但禁补记。
3. **日界线**：日键一律走 `dayKeyOf(ts, dayStart)` / `todayDayKey()`；禁 `LocalDate.now()` 当日键。
4. **Room Migration**：新增表/列必须升 version + 写 Migration + 补 `app/schemas/<v>.json`；**禁用** `fallbackToDestructiveMigration()`。
5. **静态检查器纪律**：新/修检查器必须**注入坏例自证**；本机无 JDK，CI 是唯一编译验证。
6. **依赖盲区**：本模块**无 `fragment-ktx` / `activity-ktx`** → 禁 `by viewModels()` / `commit {}` / `doOnLayout` 等扩展。
7. **尾随 lambda 纪律**：给已有 `f(..., onOk: () -> Unit)` 追加非函数型可选参数时，必须插在函数型参数**之前**。
8. **常量单一来源**：新 `const val` 前先 `grep -rnE 'const val <名字>'`（判据 = 同名且同值）。
